# VK MCP

Удалённый MCP для управления сообществами ВКонтакте: посты, комментарии,
диалоги, статистика, фото, видео и товары. Работает на сервере через
Streamable HTTP. Клиенту не требуется устанавливать локальный MCP-процесс.

**Версия 0.1:** 36 действий в проверяемом каталоге (34 метода VK и два сценария
загрузки медиа), 26 MCP-инструментов. Наличие метода в каталоге не гарантирует
доступ к нему с конкретным токеном. Живые права VK проверяются отдельно.

## Возможности

- Диагностика конфигурации, поиск и описание методов с параметрами.
- Чтение стены, комментариев, сообществ, участников, диалогов/истории,
  альбомов/фото/видео, товаров и доступной статистики.
- Планирование публикации, редактирования, комментария, сообщения, загрузки
  фото/видео. Исполнение отделено от планирования.
- Явный список разрешённых сообществ и подбор group/user/service токена.
- Одноразовые планы на 10 минут, журнал исходов, отсутствие автоматических
  повторов записи, независимое привилегированное подтверждение плана.

Токен сообщества, пользовательский токен и сервисный ключ имеют разные
возможности. Статистика и часть медиа/редактирования могут требовать
пользовательского токена, которого недостаточно просто заменить VK ID login.
Сервер не обходит ограничения VK и не выдаёт отказ API за успешную операцию.

## Разработка

Node.js 22 или новее:

```sh
npm ci --ignore-scripts
npm run check
```

Для сборки и offline-тестов токены не нужны. `npm start` запускает сервер
на `127.0.0.1`; пути конфигурации задаются через `VK_MCP_CONFIG` и
`VK_MCP_HTTP_TOKEN_FILE`. Это защищённые файлы, доступные только root/службе;
токены не передаются аргументами инструментов или URL.

Пример содержимого конфигурации (значения credentials заполняются только
в защищённом серверном файле):

```json
{
  "communities": [],
  "tokens": {},
  "writesEnabled": false,
  "approvalDir": "/etc/vk-mcp/approvals",
  "stateDir": "/var/lib/vk-mcp",
  "port": 8865,
  "allowedHosts": ["127.0.0.1", "mcp.example.com"],
  "allowedOrigins": []
}
```

После подключения сообществ `tokens.group` содержит объект ID → токен;
необязательные `tokens.user` и `tokens.service` используются по требованиям
метода. ID в `communities` положительные; `owner_id` для стены отрицательный.
Параметры конкретного метода доступны через `vk_describe_method`.
При пустой конфигурации сервер работает и возвращает `not_configured`.

## Подключение клиентов

Reverse proxy публикует `/mcp` по HTTPS и сохраняет заголовок
`Authorization: Bearer <server credential>`. `/health` также требует bearer.
Клиентам с custom headers достаточно HTTPS URL и отдельного server credential.
VK-токены клиентам не передаются. Не помещайте bearer в URL или публичный JSON.

Для облачных клиентов, которым нужен OAuth, разверните отдельный
MCP-совместимый OAuth resource server/proxy с owner gate, PKCE, точными
redirect URI и проверкой audience. Этот публичный core не содержит чужих
учётных данных или готового публичного доступа. Возможности конкретного
клиента, его вход и Refresh каталога проверяются отдельно от запуска сервера.

## Записи и подтверждения

Запись выключена по умолчанию. После отдельного включения write-профиля:

1. Агент вызывает `vk_plan_write` либо именованный `*_plan` инструмент.
2. Владелец проверяет метод, сообщество и содержимое плана.
3. Привилегированная owner-сессия отдельно разрешает ровно этот hash:

```sh
sudo python3 deploy/approve.py --config /etc/vk-mcp/config.json \
  --plan-id PLAN_ID --hash FULL_PAYLOAD_HASH
```

4. Агент вызывает `vk_execute_write` с plan_id и confirmation из плана.

MCP-клиент не может сам создать root-owned approval receipt. Строка
confirmation связывает payload, но сама по себе не подтверждает волю человека.
Истечение, изменение конфигурации или повторное исполнение отклоняются.
`unknown` означает: сначала сверить фактический исход в VK, не повторять запись.

## Медиа и ограничения

Загрузка берёт публичный HTTPS URL, а не произвольный путь на сервере.
Проверяются DNS/IP каждого соединения, перенаправления, MIME из HTTP-заголовка
и размер. MIME не означает проверку декодером. По умолчанию скачивается до
20 MiB, до трёх redirects; поддержаны JPEG/PNG/WebP для фото и MP4 для видео.
Upload направляется только на разрешённые VK-хосты и не повторяется.
Совместимость реального upload host и права токена требуют live-проверки.
После video.save ролик может ещё обрабатываться.

HTTP: до 1 MiB запроса, до 120 авторизованных запросов в минуту на процесс.
VK responses ограничены 4 MiB; rate limit между API вызовами 350 ms.
Пагинация явная через параметры метода; сервер не выгружает всю базу без лимита.
Удаления, произвольный execute, обход прав, реклама и личная лента не включены.

Планы содержат исходный payload и хранятся в каталоге службы 0700; журнал
содержит только ID, hash, метод и статус. Не отправляйте эти файлы в GitHub.
В 0.1 автоматического удаления планов/журнала нет: оператор задаёт политику
хранения и не удаляет неизвестные исходы до сверки.

## Серверный выпуск

`deploy/install.py` устанавливает точный Git SHA, собирает и тестирует его
под отдельным build UID, затем включает изолированную systemd-службу.
Имеющийся посторонний unit/config не перезаписывается. Пример dry-run:

```sh
python3 deploy/install.py --sha FULL_COMMIT_SHA --public-host mcp.example.com
```

Добавьте `--apply` для установки от root. При обновлении сохраняется предыдущий
релиз; `--rollback --apply` переключает на него. Первой установке предыдущий
релиз недоступен. Изменения формата состояния требуют отдельного migration /
backup-плана; не подменяйте откат кода откатом данных.

`--auto-update` включает серверный таймер: каждые пять минут он проверяет main
и обновляет только точный SHA с успешным manual CI. Без изменений и до окончания
CI таймер молчит; upstream-проекты автоматически не подтягиваются. Root-loader хранится отдельно
в /usr/local/lib/vk-mcp и не заменяется кодом нового релиза. Изменение самого
loader требует отдельного операторского выпуска; npm-сборка изолирована UID
и systemd cgroup без доступа к секретам.

CI запускается вручную через workflow_dispatch один раз для итогового набора.
