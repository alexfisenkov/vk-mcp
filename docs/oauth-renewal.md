# Обновление OAuth-токенов

Core не выдаёт OAuth-токены. OAuth работает в отдельном owner proxy;
credentials VK, server bearer и OAuth credentials клиента — разные уровни.
Нажатие «Обновить инструменты» обновляет каталог, а не проверяет refresh grant.

В одном действующем ChatGPT-подключении 2026-10-20 проверено автоматическое
обновление после естественного истечения access-токена. Перед вызовом его
срок уже прошёл примерно 45 минут назад. Настоящий вызов `vk_status` через
облачный коннектор вернул configured без нового входа. Независимое чтение
безопасных метаданных зашифрованного store подтвердило новый часовой access,
новую запись refresh и отсутствие старой активной refresh-записи.
Значения токенов и идентификаторы сессии не извлекались в отчёт.

В этом proxy access действует 3600 секунд; refresh имеет конечный срок.
Результат не означает бессрочный доступ и не распространяется на произвольную
установку OAuth proxy. Его pinned SDK выдаёт downstream refresh при наличии
upstream refresh; эту предпосылку нужно проверять отдельно в своём провайдере.

Регрессионная проверка private proxy на закреплённом SDK покрыла восемь
сценариев с синтетическими credentials: обновление после истечения, ротацию,
отказ старому refresh, повторное открытие зашифрованного дискового store,
привязку к клиенту/ключу/виду токена, owner gate и недоступность upstream.
Эти тесты относятся к отдельному proxy, а не к npm-тестам публичного core.

## Как повторить проверку

1. Зафиксировать только срок access/refresh и количество записей store.
   Не выводить токены, JTI, ключи подписи, хеши и имена файлов с grant ID.
2. После естественного истечения access вызвать `vk_status` из того же
   облачного подключения. Не обменивать refresh клиента вручную: ротация
   сделает сохранённую у него копию недействительной.
3. Сопоставить успешный вызов без login с новыми временными метками store.
   Один HTTP 200 без проверки срока старого access не доказывает обновление.
4. Проверить отдельными fixtures ротацию и восстановление store после
   пересоздания provider. Не удалять production state для имитации сбоя.

Повторный вход может потребоваться после отзыва GitHub-доступа, истечения
refresh, смены signing key или потери состояния. Persistent encrypted state
и signing key сохраняются между выпусками; откат кода их не пересоздаёт.
Реальный restart, аварийная потеря диска и Claude этим тестом не подтверждены.
