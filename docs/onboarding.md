# Установка и подключение

Дата проверки пути: 2026-10-20. Все домены и ID ниже — примеры.
Агент сначала читает этот документ, [диагностику](troubleshooting.md) и
[восстановление](recovery.md). Не публикуйте конфигурацию или результаты
чтения личных сообщений; в отчёт достаточно статуса и счётчика записей.

## 1. Linux VPS без VK-ключей

Предпосылки: операторский SSH/sudo, Git, Python 3, Node.js >=22, npm,
systemd и HTTPS reverse proxy. Node.js должен быть доступен системной службе
по `/usr/bin/node`; установка только в пользовательском nvm/home для этого unit не подходит. DNS и сертификат своего домена настраиваются
отдельно. Порт core 8865 слушает только loopback, его не нужно открывать наружу.

В проверенном checkout выберите полный 40-символьный SHA выпуска и
самостоятельно проверьте успешный CI именно этого SHA перед ручной установкой.
Ручной installer CI не проверяет; автоматический updater проверяет.

```sh
python3 deploy/install.py --sha FULL_COMMIT_SHA --public-host mcp.example.com
sudo python3 deploy/install.py --sha FULL_COMMIT_SHA --public-host mcp.example.com --apply
sudo systemctl is-active mcp-vk
```

Первый вызов — dry-run проверки аргументов, не проверка всех зависимостей.
Установщик создаёт отдельные runtime/build UID, защищённые config/bearer,
состояние и systemd unit. Чужие существующие unit/config не перезаписываются.
Default paths: `/srv/vk-mcp`, `/etc/vk-mcp`, `/var/lib/vk-mcp`.
При изменённых путях передавайте одинаковые `--root`, `--config-dir`,
`--state-dir` во все install/update/rollback операции.

Адаптируйте [nginx.example.conf](../deploy/nginx.example.conf), проверьте
`nginx -t`, затем reload. Шаблон не выпускает TLS-сертификат автоматически.
Proxy должен сохранять bearer и Host. В этом шаблоне внешний URL — `https://mcp.example.com/vk/mcp`;
`https://mcp.example.com/vk/health` также требует bearer. Получайте server bearer из защищённого файла
через выбранный secret manager/защищённый клиентский ввод, не печатайте его в чат.
VK-токен и server bearer — разные секреты.

Для acceptance используйте MCP SDK: `initialize` → `tools/list` → `vk_status`.
Transport stateless, ответы JSON; клиенту нужен корректный Accept для JSON/SSE.
Без VK credentials ожидается `not_configured`, включая `isError: true` у status.
Это не сбой HTTPS или MCP. Анонимный запрос должен получать HTTP 401.
OAuth discovery и работа core не доказывают вход/Refresh в облачном клиенте.

## Подключение локального клиента к удалённому серверу

Mac здесь может быть машиной клиента: MCP-процесс работает на VPS, локально
ставить копию сервера не требуется. Для совместимого HTTP MCP-клиента оператор
предоставляет URL `https://mcp.example.com/vk/mcp` и **server bearer**. В настройках
клиента выбираются Streamable HTTP и заголовок `Authorization: Bearer …`; значение
попадает только в защищённое хранилище клиента, не в project JSON/Git/команду.
Это server credential, а не community/service ключ VK. Названия полей интерфейса
зависят от клиента; сначала проверьте его поддержку URL и custom headers.

Пример для Codex CLI после передачи bearer через secret manager/скрытый ввод
в переменную окружения `VK_MCP_SERVER_BEARER`:

```sh
codex mcp add vk --url https://mcp.example.com/vk/mcp --bearer-token-env-var VK_MCP_SERVER_BEARER
```

В команде сохраняется только имя переменной. Переменная должна быть доступна
процессу Codex: desktop-приложение, запущенное отдельно, не наследует её из
произвольного Terminal автоматически. Проверить регистрацию можно `codex mcp list`,
но это ещё не сетевой тест: нужны initialize/list/status и реальный read.
Флаги сверены с `codex mcp add --help` и [официальной документацией](https://learn.chatgpt.com/docs/developer-commands#codex-mcp).

Если клиент требует OAuth или не умеет custom headers, оператор отдельно
разворачивает защищённый MCP OAuth proxy и выдаёт **его URL**, client ID/method
при необходимости. Затем пользователь проходит owner login, проверяет каталог
и vk_status внутри клиента. Не вводите VK app/client secret в настройки MCP
вместо нужных credentials. Этот core и registration-only URL сами OAuth не
реализуют; UI-вход/Refresh ChatGPT и Claude пока не подтверждены.

## 2. Токен сообщества

1. Войдите в VK под администратором нужного сообщества.
2. Откройте сообщество → «Управление» → «Работа с API» (возможен раздел
   «Дополнительно») → «Ключи доступа» → «Создать ключ».
3. Выберите необходимые права доступных разделов, подтвердите запрос VK.
   Названия и доступность пунктов зависят от интерфейса/прав администратора.
4. Получите числовой ID именно сообщества. Короткое имя не раскрывает ID;
   не угадывайте его и не подставляйте ID личного профиля.
5. На Linux-сервере из интерактивной SSH-сессии выполните:

```sh
sudo python3 /srv/vk-mcp/current/deploy/configure.py --root /srv/vk-mcp --config-dir /etc/vk-mcp
```

Для удалённого запуска используйте SSH с `-t`, чтобы был TTY. Сначала введите
положительный ID, например `123456789`, затем ключ в скрытый запрос getpass.
Невидимый ввод нормален. Не вставляйте ключ в команду, URL, tool args или чат.

Helper проверяет self-ID ключа через VK без переданного group_id и совпадение
с введённым ID, сохраняет backup, валидирует и атомарно обновляет config.
Существующий ключ он не заменяет; `writesEnabled` остаётся false.
При неизвестном исходе сначала read-back, не запускайте повторно вслепую.
Успех helper означает проверку метаданных/принадлежности, не всех возможностей.

## 3. Сервисный ключ приложения

Он нужен для проверки методов, которым group token не подходит, например
публичной стены; статистику, загрузку и все медиа он автоматически не открывает.

Откройте [создание приложения VK](https://vk.com/editapp?act=create).
[Сторонняя инструкция](https://github.com/bulatko/vk-mcp-server/blob/master/docs/SETUP.md)
описывает Standalone → настройки → сервисный ключ. Современная форма может
предлагать Web-регистрацию: в наблюдавшейся форме обязательны оба поля:

- базовый домен: `mcp.example.com` без схемы и пути;
- доверенный Redirect URL: `https://mcp.example.com/vk/registration`.

Сначала оператор разворачивает registration location из nginx-шаблона.
Он возвращает статический текст: GET/HEAD без query — 200, непустой query — 400,
прочие методы — 405. Не принимает, не обменивает и не сохраняет OAuth-коды.
Не используйте callback чужого входа и не называйте эту страницу VK OAuth.
Наблюдавшийся мастер после обязательных полей перешёл к шагу 3 из 4 —
«Способы быстрого входа в web-приложении». На нём выбирается «Настроить позже»:
виджеты входа для service key не настраиваются. Затем скриншот подтвердил уведомление «Приложение создано». На странице
«Приложение» блок «Ключи доступа» расположен ниже информации о приложении:
закройте уведомление и прокрутите вниз. Затем сервисный ключ был получен и прошёл проверку чтением стены. Точные
сохранённые URL в настройках отдельно не перечитывались.
Если нужного поля нет, остановитесь на экране без секретов и уточните текущий
официальный путь; не выбирайте другой тип credentials наугад.

Нужен именно **сервисный ключ доступа**, не client secret/защищённый ключ.
Когда ключ получен, запустите в интерактивной серверной сессии:

```sh
sudo python3 /srv/vk-mcp/current/deploy/configure.py --root /srv/vk-mcp --config-dir /etc/vk-mcp --service
```

Режим требует уже подключённого сообщества и отсутствующего service key;
проверяет wall.get с count=1 и форму ответа до сохранения, не заменяет group token.
По умолчанию проверяется первое сообщество; для нескольких сообществ можно
добавить `--community-id 123456789`, но только ID из существующего allowlist.
Защищённый ввод service key и последующее чтение стены через HTTPS MCP
подтверждены в одном живом подключении. Это не доказывает остальные методы:
wall.getComments и photos.getAlbums с этим ключом вернули VK1051.

Helper берёт `onboard.lock` в config-dir. Все другие писатели конфигурации
должны брать тот же lock; ручное редактирование параллельно запрещено. Проверка
байтов перед atomic replace не является kernel CAS против произвольного root.
Штатный installer существующий config.json не переписывает.

## 4. Приёмка и дальнейшие обновления

Проверьте `vk_status`, затем `vk_describe_method` и ограниченный read для
каждой нужной возможности. Для стены используйте отрицательный `owner_id`,
например `-123456789`; для комментариев — настоящий post_id из прочитанной стены.
Не отправляйте сообщения и не публикуйте тестовый пост без отдельного разрешения.

`--auto-update` у install.py включает проверку main каждые пять минут:
устанавливается точный SHA только с успешным manual CI. Root-loader отделён;
его обновляют явно через `--refresh-loader --auto-update` из проверенного релиза.
Откат: тот же install.py с `--rollback --apply` и прежними путями/host.
Первая установка не имеет предыдущего релиза. Откат кода не откатывает данные.
Для записи: включённый профиль → план → проверка владельцем → отдельный
`sudo python3 deploy/approve.py --config /etc/vk-mcp/config.json --plan-id PLAN_ID --hash FULL_PAYLOAD_HASH`
→ исполнение плана. Подтверждение строкой MCP не заменяет root receipt.
